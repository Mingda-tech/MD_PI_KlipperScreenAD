# Klipper 上位机纯软件更新包

本包只更新 `/home/mingda/klipper` 的上位机程序，使用项目既有虚拟环境与打印配置。
它不携带独立 MCU 更新镜像，不运行 CAN、USB、DFU 或 Linux MCU 刷写工具，
不修改 `printer.cfg`、`load_cell.cfg`、校准或 `SAVE_CONFIG`，也不更改系统服务定义。

建议先安装配套 KlipperScreen 软件包，再从屏幕确认安装本包。未登记旧版本或旧版本
无法识别时显示“未知”，仍可在来源、设备状态、备份和恢复校验通过后继续升级。
已知降级、现场受管源码修改、源目录损坏或配置冲突仍会在执行前拒绝。

目标源为用户指定的 `Mingda-tech/MD_PI_klipper` 仓库。仅发布说明显式允许时，
才支持从已核实的 `Mingda-tech/KlipperAD` 来源迁移；只在暂存的新 Git 目录切换
origin，原备份保留原地址。恢复原程序时原 Git 配置一并恢复。

## 安装与验证

1. SWUpdate 验签并完整复制物料。包内预检只读核对实际服务进程、主配置及全部 include、
   打印/暂停/校准/温度状态、软件来源和现有 Python/GCC 依赖。
2. 在 Klipper 同一文件系统暂存 Git 版本、离线重建 `c_helper.so`、检查活跃扩展依赖，
   并测试实际 `RENAME_EXCHANGE` 能力。暂存通过前不停止现有程序。
3. 保存私有恢复记录，再次核对状态与配置；仅停止和启动 `klipper.service`，原子切换程序目录。
4. 验证 Klipper ready、所有原 MCU 连接和硬件身份及可识别的原固件版本、打印配置摘要均不变。
   `startup` 期间只等待，包含 CAN 节点识别较慢的情况；已 ready 时不请求额外复位。
   仅在同一服务进程的 `error`/`shutdown` 状态和错误消息持续稳定至少一秒、全部原 MCU
   已完成识别且硬件和连接一致、配置未变且设备确认空闲时，才至多请求一次应用固件重启；
   请求前再次核验状态。请求超时也不重复发送，该动作不写入固件或 Bootloader。

失败时保留原程序备份与同任务物料。若原程序未被替换，不打断原程序的打印。
已切换程序但设备明确正在打印、暂停、校准或加热时，不自动回退等待原任务恢复。
其余失败可以恢复原软件并重新验证；没有确认结果不会标记升级完成。

掉电期间始终保留目标程序路径；开机不会自动刷写或重放升级，需要屏幕原任务显式恢复。
本包与 KlipperScreen 的现有自检逻辑无关，不修改或关闭自检功能。

仅在目标机现有 `mingda` 服务布局、Python 环境、配置结构和物料验证通过时安装。
所有文件级备份和 `klipper-software-state.json` 均保存在原离线任务和程序同级私有目录。
安装和回退的健康等待会在任务内写入权限为 `0600` 的 `klipper-software-health.json`，
记录有限的状态变化与经截断、脱敏的错误消息；不记录环境变量或完整配置。预检仍然只读。
